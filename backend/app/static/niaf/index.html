§1 The problem

Agents increasingly retrieve from personal media libraries. Almost nobody measures whether they find the right thing.

The Model Context Protocol made it trivial to hand an agent a search tool over your own files. What it did not do is tell you whether that tool is any good. The retrieval task underneath — short-form, personal, multimodal, and answered at clip granularity rather than document granularity — falls between the existing benchmarks. Video-MME and its successors measure question answering over a video you already have. MVEB and MMEB measure embedding quality in isolation. Neither one measures a system, end to end, answering the question a person actually asks their agent: find me the bit where she does the thing.

NIAF-Bench measures that. Before the scorecard, one query, with both systems' output shown blind. Decide which list you would rather have been handed.

§2 What NIAF-Bench measures

2.1 The task

A natural-language query goes in. A ranked list of videos comes out, each optionally carrying a clip span. Every system is reached through one adapter interface — search(query, signals, limit) returning hits with doc_id, rank, score, an optional clip_span, and per-leg evidence. A BM25-on-transcript baseline ships alongside the two real systems to prove the interface is not shaped around either of them.

2.2 The corpus

videos, stratified by content category so every slice has enough mass to report. Composition matters as much as size: without near-miss distractors, precision is free and the benchmark flatters everyone.

2.3 Query intents

Every query carries an intent bucket and the signals it is expected to need. Expectations are diagnostics — they answer "did the leg we thought would fire actually fire?" They never configure the run.

    2.4 Judging

    Top-k from every arm is pooled and the union judged blind to which system produced it, graded 0–3: 3 is the video meant, 2 a strong alternative, 1 acceptable, 0 not relevant. Judgments live in their own file keyed (query_id, doc_id), separate from the query set — so adding an arm surfaces “ docs in pool are unjudged” instead of quietly scoring them zero.     §3 Keeping it fair

    The hard part of a two-system comparison is not the metric. It is that the systems are not built the same way, and any naive mapping of one's components onto the other's quietly hands somebody an advantage.

    NIAF-Bench resolves this with one indirection: arms are declared over abstract signals, and each adapter declares how — or whether — it expresses each one. The runner refuses to run a strict-parity arm containing a signal an adapter cannot express, rather than silently dropping it.

    3.1 The three arms

    • Arm A — strict parity. visual_action + speech only. Distill runs two of its six legs.
    • Arm B — best foot forward. Each system at full strength. Answers the product question: which tool finds my clip today.
    • B − A — the delta. Exactly how much of Distill's standing comes from metadata TwelveLabs was never given. A first-class result, not a footnote.
    An asymmetry worth stating up front. TwelveLabs exposes one audio index; speech and ambient audio cannot be separated through its API. Its Arm A and Arm B configurations are therefore identical, and every TwelveLabs figure on this page is the same number in both arms. The parity restriction binds only on Distill — which, if anything, makes Arm A harsher on Distill than a true parity arm would be.

    3.2 Disclosure

    I built Distill. That is a real conflict and no amount of methodology erases it. What it buys instead: judging is blind to system, every judgment is published keyed to (query_id, doc_id), the headline claim is taken from the arm where Distill is weakest, and the raw run artifact ships so anyone can rescore it against their own judgments without re-querying either system. If a number here is wrong, it should be cheap to prove.

    §6 A living benchmark

    Most video benchmarks stagnate because they ship as a static leaderboard and a paper. NIAF-Bench is versioned and carries a changelog; every run stamps a fingerprint covering the git SHA, embedding model, index ID, fusion constant and concurrency, so two scorecards are only comparable when their fingerprints say they are.

    The split that makes this maintainable is runner ≠ scoring. Searching is slow and costs money; scoring is a pure function from stored artifact plus judgments to scorecard, with no network and no database. Adding a metric, fixing a judgment, or re-bucketing queries costs nothing and re-queries nobody.

    Adding a system means implementing one adapter and declaring its capability matrix. The BM25 baseline exists to keep that interface honest. TwelveLabs is the first system evaluated here, not the benchmark's subject — if you maintain a video retrieval system and want a row, the adapter is about eighty lines and I will run it.

    §7 Reproduce it

    Everything on this page comes out of three commands against a published corpus manifest and judgment file.

    Raw run artifact, judgments, query set and the scoring code live in the repo. The compare subcommand diffs against the last archived artifact, so a regression reads as “nDCG@10 −0.04 on spoken-claim, driven by the transcript leg” rather than a number that moved.
